# РЕГЛАМЕНТ ЗОНЫ server/ (хакатон)

Codex и Claude запускаем **из папки `server/`**: Codex складывает правила `../AGENTS.md` (общие) + этот файл (зона `server/`), ближний главнее.
Общие правила репо — `../AGENTS.md`: договор с экраном, git, **коммит часа**. Здесь они не повторяются и не отменяются.
Этот файл — закон для всех ролей в зоне `server/`. Выше `server/` (`../web/`, `../contract/`, корень) агенты не пишут; `../contract/` правит только Прораб.
Если ты Codex/мелкая модель — ты **СЛЕСАРЬ**, твои правила в разделе 7.

## 1. РОЛИ

| Роль | Кто | Что делает | Код пишет? |
|------|-----|-----------|-----------|
| **ПРОРАБ** | большая модель (Claude) | разбирает кейс, архитектура, контракт, выдаёт наряды, принимает работу, ADR | НЕТ |

## 4. ЗАКОНЫ (для всех)

1. **Один наряд = одна зона.** Трогать файлы вне наряда — нарушение.
2. **Доказательство, не слова.** «Готово» без вывода команды = не готово.
3. **Контракт — закон.** Поля, типы, эндпоинты — строго по `../contract/openapi.yaml` и `../contract/examples/`. Менять — только Прораб + ADR + согласие Виталия.
4. **Улучшения — не внедрять самому.** Заметил → `IMPROVEMENT REPORT`. Решает Прораб.
5. **Секреты — никогда в код и логи.** Ключи только через `.env` в **корне репо** (движок читает `../.env`). Новый ключ → сразу строка в `../.env.example`. Агентам чтение `../.env` закрыто.
6. **Минимальный контекст.** Читай то, что указано в `КОНТЕКСТ` наряда, а не весь проект.
7. **Работающий end-to-end > количество фич.**

## 5. ПРОТОКОЛ ПАРАЛЛЕЛЬНОЙ РАБОТЫ

- Слесарь берёт наряд, только если: статус `ВЫДАН` **и** все `ЗАВИСИТ ОТ` в статусе `ПРИНЯТО` **и** «Исполнитель» пуст или совпадает с его именем.
- **Захват:** первым делом в `naryady/INDEX.md` и в шапке наряда — `В РАБОТЕ (слесарь-<N>)`. Занятый наряд не трогать.
- Прораб гарантирует: у параллельных нарядов файлы не пересекаются.
- Общие файлы (`requirements.txt`, `../.env.example`) — только дописывать строки. Факт — в отчёт. (`../.env.example` лежит выше `server/`: строку дописывает Прораб по `ВОПРОС ПРОРАБУ`, либо наряд явно разрешает.)
- `server/` и `web/` связаны только через API по договору. Пока движок не готов, экран Виталия работает на образцах из `../contract/examples/`.

## 6. ЖИЗНЕННЫЙ ЦИКЛ НАРЯДА

```
ВЫДАН → В РАБОТЕ → НА ПРОВЕРКЕ → ПРИНЯТО
                        ↓
                     ВОЗВРАТ → В РАБОТЕ
В РАБОТЕ → ЗАБЛОКИРОВАН (причина) → Прораб решает
```
`ВЫДАН / ПРИНЯТО / ВОЗВРАТ` ставит Прораб. `В РАБОТЕ / НА ПРОВЕРКЕ / ЗАБЛОКИРОВАН` — Слесарь.

## 7. СЛЕСАРЬ — ТВОИ ПРАВИЛА

Ты — Implementation Agent. Senior-инженер: делаешь ровно наряд, быстро и доказуемо.
**Ты не угадываешь.** Интерфейс — в наряде дословно, форма кода — в эталоне, типы — сгенерированы из контракта, API библиотек — context7. Чего-то нет → `ВОПРОС ПРОРАБУ` (раздел 11).

### Перед работой
1. `naryady/INDEX.md` → выбери наряд по разделу 5 → захвати.
2. Прочитай наряд целиком, всё из `КОНТЕКСТ` и разделы эталона из `ЭТАЛОН`.
3. Проверка наряда (2 мин): противоречит контракту / невыполним / есть явно лучший путь → раздел 11.

### Алгоритм: план → тест → код → самопроверка
1. **План** в отчёт, ≤ 5 строк: файлы, порядок, что вызывает что.
2. **Тест первым.** Каждый ПРИМЕР наряда → тест в `temp/<ID>/`. Запусти — **красный**. Зелёный до кода = тест ничего не проверяет.
3. **Код по эталону.** `naryady/spravka/ETALON_SERVER.md` — скопируй структуру, замени имена. Интерфейс — дословно из наряда.
4. **Зелёный полигон → перенос** в код зоны `server/` (только файлы из таблицы ФАЙЛЫ).
5. **Самопроверка** — чек-лист в отчёте, честно.
6. **DoD** — КАЖДАЯ команда из `КРИТЕРИЙ ПРИЁМКИ`, реальный вывод (≤ 10 последних строк). Плюс все тесты своей зоны.
7. **Вики** по разделу 8. **Отчёт** + `IMPROVEMENT REPORT`.
8. **Коммит и отправка наряда** (раздел 13): только файлы из таблицы ФАЙЛЫ, `git pull --rebase --autostash && git push`, хеш — в отчёт. Только при зелёном DoD. Раз в 20 минут — промежуточный коммит (раздел 13).
9. **Статус** → `НА ПРОВЕРКЕ` (в наряде и в `INDEX.md`), одна строка человеку.

Образец отчёта, который принимается с первого раза, — `naryady/_PRIMER.md`.

### Стоп
3 попытки подряд без зелёного DoD → `ЗАБЛОКИРОВАН`: что пробовал, точная ошибка, гипотеза.
Не можешь проверить → `НЕ ПРОВЕРЕНО: <что> — <почему>`. Вывод не выдумывать.

### Запрещено
- «Заодно поправил», файлы вне наряда.
- Писать выше `server/` (`../web/`, `../contract/`, корень репо). Контракт правит только Прораб.
- Менять секции наряда выше `ОТЧЁТ СЛЕСАРЯ`, ставить `ПРИНЯТО`.
- Менять контракт, `naryady/DECISIONS.md`, сгенерированные типы.
- Переписывать файл > 50 строк без копии `temp/<ID>/<имя>.bak`.
- Добавлять зависимость без строки в отчёте.

## 8. ВИКИ (LLM-wiki по Карпатому)

Код хранит **ЧТО**, вики хранит **ПОЧЕМУ** и **СВЯЗИ**. Вся вики — только в `naryady/wiki/`.

### Метод (Андрей Карпатый, «LLM Wiki»)
Обычно агент каждый раз заново «изучает проект»: читает файлы, тратит токены, забывает. У Карпатого знание **компилируется один раз** в вики и дальше только дополняется. Агент читает не код, а вики: это короткие связанные страницы, которые он сам же и написал.
Три слоя:
- **Источники**: код, кейс, контракт. Правда, но читать их дорого.
- **Вики**: выжимка из источников в виде страниц, связанных ссылками `[[имя]]`. Её пишет и держит в порядке только агент.
- **Схема**: этот раздел. Правила, как вики устроена.

Три операции, и каждый агент выполняет их сам, без напоминаний:
1. **Ingest (записать).** Сделал работу → обнови страницу модуля (создай, если её нет), связи в `depends_on`/`used_by` у обеих сторон, `index.md` и строку в `log.md`. Одна задача задевает несколько страниц — это норма.
2. **Query (спросить).** Перед работой сначала `index.md` → нужные страницы → и только потом код, по конкретным строкам. Нашёл в коде ответ, которого не было в вики → запиши его в вики (ingest). Знание накапливается и не теряется.
3. **Lint (проверить).** Раз в ~60 мин: битые ссылки, невзаимные связи, страницы без строки в index, модули без страниц, противоречия вики и кода. Правит агент.

Проверка, что вики живая: новый агент с нулевым контекстом по `index.md` за 2 минуты понимает, где что лежит и почему сделано так.

```
naryady/wiki/
  SESSION.md        состояние смены (пишет Прораб)
  index.md          каталог: [[имя]] — суть, одна строка на страницу
  log.md            журнал, только дописывать в конец
  case.md           разбор кейса (Прораб)
  architecture.md   схема, модули, граф вызовов (Прораб)
  modules/<имя>.md  страница модуля (Слесарь), шаблон — modules/_SHABLON.md
```

Во frontmatter страницы модуля — граф связей и происхождение знания (поля происхождения по Карпатому: откуда взято, когда, насколько уверены):
```yaml
depends_on: [[llm-client]]     # кого использую
used_by: [[api-score]]         # кто использует меня
adr: [ADR-003]
last_naryad: D-007
sources: [services/score.py, ../contract/openapi.yaml]  # откуда знание — код/договор/кейс
updated: 15:20                 # время последней правки страницы
confidence: высокая            # высокая / средняя / догадка — Прораб на приёмке верит соответственно
```

1. **Ссылки** — только `[[имя-страницы]]`.
2. **Двусторонность.** `A depends_on B` → `A` в `used_by` у `B`.
3. **Код ↔ вики.** Первая строка главного файла модуля: `# wiki: naryady/wiki/modules/<имя>.md` (в TS: `// wiki: ...`).
4. **Смена интерфейса** → во все `used_by` строку `⚠ <ID>: изменился интерфейс <модуля> — проверить`. Чужой код не трогать.
5. **«Почему так»** — причина и отброшенные альтернативы, ссылка на ADR.
6. **Новая страница** → строка в `index.md`. **Каждый наряд** → строка в `log.md`: `## [ЧЧ:ММ] D-007 | модуль | что изменилось`.
7. **Ответы — в вики, а не только в чат.** Слесарь или Прораб разобрался в чём-то нетривиальном (почему падал внешний API, откуда взялось число кейса, как связаны два шага пайплайна) → это отдельная страница или раздел «Подводные камни», а не одноразовый ответ в чат. `confidence: догадка` — пока не проверено кодом/выводом; после проверки поднять до `высокая`.

### Lint вики — что ищем (раз в ~60 мин, скилл `/lint-wiki`)
- битые `[[ссылки]]`; страницы без строки в `index.md`; модули в коде без страницы;
- невзаимные `depends_on` / `used_by`;
- висящие `⚠ проверить` после смены интерфейса;
- **страницы-сироты**: ни один `depends_on`/`used_by`/`index.md` на них не ссылается;
- **противоречия вики и кода**: `sources` указывает на файл, которого уже нет, или сигнатура в вики не совпадает с кодом (спросить `razvedchik`);
- **устаревшее знание**: `updated` старше последнего `last_naryad` модуля — страницу не обновили после правки кода;
- `confidence: догадка`, провисевшая больше одной волны, — либо проверить, либо удалить.

## 9. КОД: СТРУКТУРА, СВЯЗИ, ПРАВИЛА

### Структура (фиксирована; корень = папка `server/`)
```
main.py  config.py  errors.py        приложение, настройки из .env, AppError
api/<ресурс>.py        роутеры: принять → вызвать сервис → вернуть. 0 логики
services/<имя>.py      бизнес-логика и пайплайн
clients/llm.py         ЕДИНСТВЕННАЯ точка вызова LLM: structured output + деградация
clients/<api>.py       по файлу на внешний API
db/repo.py             все SQL-запросы
schemas/contract.py    ГЕНЕРИРУЕТСЯ из ../contract/openapi.yaml — руками не править
prompts/<имя>.md       промпты LLM, переменные {{var}}
demo/<имя>.json        демо-ответы (DEMO_MODE и последнее звено деградации)
data/                  данные кейса (в репо); путь — DATA_PATH из ../.env
tests/                 requirements.txt  pytest.ini
(.env и .env.example — в КОРНЕ репо, не в server/)
```

### Связи — только сверху вниз
```
server:  api → services → clients / db        (schemas, errors, config — доступны всем)
```
Обратный импорт — ошибка. `api/` не ходит в `clients/` и `db/` напрямую. Экран (`../web/`) с движком связан только HTTP по договору.

### Правила
1. **Два вида вызова LLM — только через `clients/llm.py`.** Реплика бота пользователю → `complete_chat` (текст). Всё, что дальше читает код (классификация, извлечение, решения шагов) → `complete_structured` (Pydantic-схема). Свободный текст кодом не парсить.
2. **Типы контракта генерируются:** `schemas/contract.py` (datamodel-codegen из `../contract/openapi.yaml`).
3. **Цепочка деградации:** основной LLM → запасной → демо-ответ. Демо работает всегда.
4. **Таймаут и ретраи** на каждый внешний вызов (30 с, 2 ретрая).
5. **Валидация на входе** каждого шага; ошибки — по контракту `{error, code}`.
6. **Логи шагов:** `[шаг] … ok/fail время`. Без секретов.
7. **Промпты LLM — файлами** в `prompts/`, не строками в коде.
8. **Имена:** Python `snake_case`, функции «глагол + объект»; модели — как в контракте; внутренние схемы LLM — `_LLM<Имя>`; коды ошибок — `UPPER_SNAKE`.
9. **Автопроверка.** В Claude Code хук после каждой правки ловит синтаксис, неопределённые имена, битый JSON/YAML и ключи в коде — чини сразу. В Codex сам запускай `ruff check` после каждого файла.
10. **Переносимость venv ↔ docker — код не знает окружения.** Ни одного захардкоженного пути, хоста, порта, URL. Всё — из `.env`/`config.py`:
    - пути только **относительные** от `server/` или из переменной (`DATA_PATH`); никаких `C:\...`, `/app/...`, абсолютных путей;
    - сервер слушает `HOST=0.0.0.0` из `.env`, **не `127.0.0.1`** (иначе не видно из докера);
    - порт — из `PORT`, адреса экрана — из `ALLOWED_ORIGINS`, никакого `http://localhost:8000` строкой в коде.
    Соблюдено → докер в конце (наряд `X-`) — тонкая обёртка, код не меняется ни на строку. Нарушено → при переезде в докер «всё летит». Новая переменная окружения → строка в `../.env.example` + поле в `config.py`.

## 11. ПРАВО И ОБЯЗАННОСТЬ ВОЗРАЖАТЬ

Цель — работающее демо, а не согласие. Молча сделать заведомо плохо — нарушение.

**Прораб → человеку.** Хотелка дольше/рискованнее альтернативы, ломает контракт, не влезает по времени, гиммик вместо ценности — **один раз**:
```
⚠ ВОЗРАЖЕНИЕ: <что не так, одной фразой>
Предлагаю: <альтернатива>
Почему: <1–2 аргумента: минуты, риск, ценность для демо>
Решай: А) как ты сказал  Б) как предлагаю
```
Человек выбрал → делается без повторных споров, решение → ADR.

**Слесарь → Прорабу** (через отчёт наряда):
- *Блокирующее* (противоречит контракту, невыполнимо, не хватает данных, ломает чужую зону) → код не пишет, `ВОПРОС ПРОРАБУ: <суть> | Вариант: <как лучше>`, `ЗАБЛОКИРОВАН`.
- *Не блокирующее* (можно лучше) → делает по наряду, идея — в `IMPROVEMENT REPORT`.

**Запрещено всем:** «отличная идея» без проверки, «зависит от» без рекомендации, соглашаться, чтобы не спорить.

### 11.1. Эскалация слесаря — сигнал, а не помеха (боевой опыт 21.09)

Слесарь видит код, Прораб — нет. Если слесарь пишет «наряд лечит не ту причину» — **он чаще прав**.

Случай D-011 (beauty_swarm): Прораб выдал наряд «расширить словарь `detect_subject`» — думал, что метрика падает из-за узкого словаря. Слесарь (GPT) вернул `ЗАБЛОКИРОВАН`: правило уже работает, настоящая причина — парсер вообще не извлекает нужное поле. Прораб проверил разведчиком → слесарь прав → наряд переписан → метрика поднялась.

**Протокол Прораба на `ЗАБЛОКИРОВАН` с диагнозом:**
1. **Не спорить и не передавать наряд другому слесарю.** Диагноз идёт от того, кто читал код.
2. **Проверить фактами** — `razvedchik` на точные строки, сигнатуры, поведение. Не «кажется» и не память.
3. Диагноз подтвердился → **переписать наряд**, а не уточнить формулировку. Новая причина = новый наряд.
4. Причина была архитектурной → **ADR** (почему корень оказался не там, где искали).
5. Диагноз не подтвердился → вернуть слесарю с выводом разведчика дословно.

**Запрещено Прорабу:** отмахнуться от `ЗАБЛОКИРОВАН`, повысить уровень модели вместо разбора причины, выдать тот же наряд заново «попробуй ещё раз».

## 13. GIT

Общие правила git — `../AGENTS.md`. Здесь — детали для `server/`.

- **Слесарь (Codex) коммитит и отправляет сам, без просьбы человека — один коммит на наряд, сразу после зелёного DoD** (не накапливать):
  ```
  git add <файлы из таблицы ФАЙЛЫ наряда>
  git commit -m "D-007: краткое описание" -- <те же файлы>
  git pull --rebase --autostash && git push     # push отклонён — повторить до 3 раз
  git log -1 --format=%h                        # хеш → в отчёт
  ```
  `-- <файлы>` обязателен: параллельные слесари работают в одном дереве, каждый коммитит только своё. `git add -A`, `git add .`, коммит из корня — запрещены. `index.lock` занят → подождать 3 с и повторить. `ЗАБЛОКИРОВАН` / красный DoD → не коммитить. Никакого `push --force` и `amend` отправленного.
- **Отправка каждые 20 минут** (общее правило — `../AGENTS.md`): наряд идёт дольше 20 минут с последней отправки → слесарь коммитит то, что есть, с сообщением `D-007 промежуточный: работает X, не работает Y` (только свои файлы) и отправляет. Промежуточный коммит красного кода допустим — это доказательство прогресса; статус наряда остаётся `В РАБОТЕ`.
- **Дежурный коммит часа.** По будильнику :30 (или если в :35 в этом часу нет отправленного коммита) человек запускает отдельное окно: `codex -p cheap 'Коммит часа: закоммить и отправь всё, что есть в server/ и ../contract/ (код, тест, данные, схема, заметка), по AGENTS.md §13.'` Здесь, и только здесь, агент коммитит файлы `../contract/`, написанные Прорабом. Пустых коммитов ради галочки нет — но любой реальный прогресс годится (п. 6.6).
- Коммиты слесарей идут от git-пользователя Дмитрия (`avtosubaru25` проверить в `git config user.name`/`user.email` до старта) и считаются его коммитами.
- Не коммитить: `../.env` (корневой `.gitignore`), `temp/`, `naryady/`, `.claude/`, `CLAUDE.md`, базы, ключи — `server/.gitignore` и корневой `.gitignore`. **`server/data/` коммитим** (данные кейса нужны судье для запуска).
- **Claude (Прораб, субагенты) в git не пишет и не пушит** (`git push` закрыт в `.claude/settings.json`). На 23-е код пишут только Codex-слесари по внутреннему плану команды; Положение п. 5.4.12 разрешает любые AI-инструменты и не требует Codex, если иное не установлено задачей. Вклад каждого проверяют (п. 5.4.7). Режим «слесари = субагенты Claude» — только на репетиции.
- **Строка статуса** — первой строкой в ответе Прораба и слесаря: `Сейчас ЧЧ:ММ. Последняя отправка N минут назад. Неотправленных коммитов: K.` (`date +%H:%M; git log -1 --format='%cr | %s'; git rev-list --count origin/main..HEAD`). Просрочено (>20 мин или :35 без коммита) — сначала отправка, потом ответ.
- Прораб следит: `git log -5 --format="%an %cd" --date=format:%H:%M` (считаются коммиты Дмитрия, не Виталия). Не отправлено >20 мин, или с :30 до :59 в часу нет отправленного коммита — **первой строкой** `⏰ Отправки нет N мин. Запусти дежурный коммит (AGENTS.md §13)`. Проверять в «Статус», после приёмки, перед новой выдачей.
- Конкурсную разработку и коммиты начинаем после 13:00; первый коммит и push — в 13:10, с фактическим новым результатом. После 18:00 — только чтение.
- Папки `server/` и `web/` разные → конфликтов нет. Дмитрий пушит `server/` и `contract/`, Виталий — `web/`.

## 16. КОНВЕЙЕР И БЮДЖЕТ ЛИМИТОВ

Цель: слесари работают непрерывно, а лимиты доживают до 18:00. **Узкое место по внутреннему плану — Codex**: на репетиции он кончился у Дмитрия в 17:26 (через ~4 часа). Положение п. 5.4.12 не делает Codex обязательным; работа через Codex здесь — выбор команды. Лимиты считаются окнами по ~5 часов — весь хакатон = одно окно, второго не будет.

### 16.1. Конвейер вместо «волн с ожиданием»

1. **Наряд выдаётся сразу, как готов** (прошёл тест слепого слесаря), а не когда готова вся волна. Прораб пишет наряд № 1 → человек тут же запускает слесаря → Прораб пишет наряд № 2 и т. д. Слесарь не ждёт остальных.
2. **Порядок выдачи:** сначала критический путь (D-001 каркас и всё, от чего зависят остальные), потом независимые наряды, потом остальное.
3. **Слесарь закончил** → коммит (раздел 13) → статус `НА ПРОВЕРКЕ` в наряде и `INDEX.md` → одна строка человеку. Окно закрывается.
4. **Приёмка идёт параллельно с выдачей**, не вместо неё: пришёл отчёт → `/priemka` (по отчёту и выводам DoD, код не читать) → открылись зависимые наряды → сразу выдать.
5. **Одновременно не больше 3 слесарей.** Больше — конфликты в общих файлах и сгорающий лимит; выигрыша по времени нет, упирается в приёмку Прораба.
6. Слесарь не ждёт `ПРИНЯТО` от Прораба для следующего **независимого** наряда, если тот `ВЫДАН`. Зависимый — ждёт `ПРИНЯТО` (раздел 5).

### 16.2. Уровни моделей — по умолчанию самый дешёвый

| Уровень | Кто | Когда | Что стоит |
|---------|-----|-------|-----------|
| **T1 дешёвый** | Codex: самая лёгкая модель, `reasoning_effort = low` (на 23-е — единственный исполнитель кода). Claude `haiku` — только `razvedchik` и репетиция | **по умолчанию для любого наряда**: конфиг, схемы, CRUD, роутеры, тесты по образцам, промпты, вики, `docker-compose`, README | 1× |
| **T2 средний** | Codex: средняя модель, `reasoning_effort = medium`. Claude `sonnet` — только репетиция | только если в наряде `МОДЕЛЬ: T2`: пайплайн с LLM-вызовами, расчёты, интеграция `I-` | ~4–5× |
| **T3 дорогой** | Claude: Прораб (большая модель) | архитектура, договор, наряды, приёмка, ADR. **Код не пишет** | ~15× |

Правила:
- Прораб ставит `МОДЕЛЬ: T1` по умолчанию. `T2` — только с одной строкой обоснования в наряде.
- **Эскалация:** слесарь T1 дал `ЗАБЛОКИРОВАН` после 2–3 попыток → Прораб уточняет наряд ещё раз; не помогло → один перезапуск на T2. Больше эскалаций нет: дальше режем scope. **`ЗАБЛОКИРОВАН` с диагнозом причины — это не «не справился», а находка: §11.1.**
- **Хороший наряд дешевле сильной модели.** Если T1 не справляется — сначала дописать ИНТЕРФЕЙС/ПРИМЕРЫ и `ФАКТЫ РАЗВЕДКИ` (CLAUDE.md), а не повышать уровень.
- Слесарь не читает лишнее (КОНТЕКСТ ≤ 6 файлов), длинные выводы — последние 10 строк, ответ в чат — одна строка. Это основной способ экономии в обоих инструментах.
- Прораб приёмку делает по отчёту (T3 читает только наряд), факты о коде берёт у `razvedchik` (haiku).

**Дешёвая модель тянет боевой код — проверено 21.09.** На прогоне beauty_swarm вся реализация шла слесарями на лёгких моделях: код собрался, тесты зелёные, система работает. Уровень модели — не рычаг качества; рычаг — спецификация наряда. Повышать T1→T2 имеет смысл только там, где в наряде **рассуждение** (пайплайн с LLM, расчёты, интеграция), а не объём.

**Лимит X5 — запас есть, но дефолт не меняется.** С расширенным лимитом дорогая модель перестаёт быть узким местом, и T2 можно ставить смелее: сложный наряд сразу на T2, без круга «T1 не смог → переписали → T2». Но `T1 по умолчанию` остаётся: лимит тратится на резерв под баги после 16:00, а не на то, чтобы CRUD писала большая модель.

**Подтверждённые модели исполнителя (замеры 21.09):**

| Модель | Роль | Чат / tool call | Замечание |
|--------|------|-----------------|-----------|
| `cx/gpt-5.6-luna` | основная на прогоне | 4.7 с / 5.0 с | стабильна, tool calls без сбоев |
| GPT 5.6 лёгкая | T1 по умолчанию | — | рабочий дефолт для нарядов-объёма |
| `xai/grok-4.20-0309-non-reasoning` | самая быстрая | 1.5 с / 1.1 с | быстрее Luna в 3.5× на полной цепочке |
| `ag/gemini-3.1-flash-lite-preview` | запасная | 1.6 с / 1.3 с | ставится fallback'ом |

Полный журнал замеров — в проекте beauty_swarm, `nastrouki/models_bench.md`.

**Запасная модель обязательна.** Основная модель отдаёт 503 (недоступна) или 429 (rate limit) — запрос автоматически уходит на запасную, человек ошибки не видит. Без fallback параллельный прогон 13 запросов дал 6 отказов подряд; с fallback — 13 из 13 зелёных без единой задержки. Настройка — рядом с выбором модели, одним полем `fallback`.

### 16.3. Бюджет на 5 часов (доля лимита окна, а не токены)

Два независимых лимита — считаем отдельно.

**Codex (узкое место, весь код).** Калибровка по репетиции: без политики «дешёвая модель по умолчанию» лимит ушёл за ~4 часа из 5, т. е. ~25% в час. Цель — ≤ 16% в час.

| Статья | Доля Codex | Комментарий |
|--------|-----------|-------------|
| Слесари T1 | 55% | основная масса нарядов |
| Слесари T2 | 20% | 3–4 сложных наряда (пайплайн, интеграция `I-`) |

**Claude (Прораб).** Кейс, договор, ~12–15 нарядов, приёмки, `razvedchik`. Код не пишет — этот лимит легче; но запас нужен на «Разбор» и правки договора.

**Контрольные точки** (на синке :40 человек смотрит расход: в Codex `/status`, в Claude Code `/usage` — точная команда зависит от версии):

| Момент | Codex не больше | Claude не больше | Если больше на 10+ пунктов |

### 16.4. Codex: профили и параллельный запуск

**Один раз до хакатона** — профили в `%USERPROFILE%\.codex\config.toml`. Имена моделей — подставить те, что реально есть в `/model` на ноутбуке (самая лёгкая → `cheap`, средняя → `mid`):
```toml
[profiles.cheap]
model = "<самая лёгкая из /model>"
model_reasoning_effort = "low"

[profiles.mid]
model = "<средняя из /model>"
model_reasoning_effort = "medium"
```
Проверка в `server/`: `codex -p cheap` → `/status` показывает лёгкую модель.

**Запуск волны параллельно** (PowerShell из `server/`, по окну на наряд; уровень берётся из поля МОДЕЛЬ наряда — T1 → `cheap`, T2 → `mid`):
```powershell
foreach ($id in "D-003","D-004","D-005") {
  Start-Process powershell -ArgumentList "-NoExit","-Command","codex -p cheap 'Ты слесарь-$id. Возьми наряд $id и выполни по AGENTS.md, раздел 7.'"
}
```
Наряд, выданный позже, запускается отдельным окном той же командой — не ждёт остальных (16.1).

**Только для репетиции:** в режиме Claude Code Прораб запускает субагентов `slesar` сам (`haiku` по умолчанию, `sonnet` для T2). На 23-е код пишут только Codex-окна.
