### Разбор моделью: закрытая несовместимость и оставшаяся проверка качества

Промежуточная комбинация `gpt-5-mini` с `reasoning_effort="none"` была несовместимой: [официальная документация OpenAI](https://platform.openai.com/docs/api-reference/graders?api-mode=chat) указывает, что модели до GPT-5.1 не поддерживают `none`. Команда уже закрыла это коммитом `b7b8c35`: `akim/explainer.py` выбирает `gpt-4.1-mini`, обёртка не передаёт ей reasoning-параметр, README и `.env.example` согласованы. В коммите зафиксирован живой результат `mode="llm"` примерно за 3,0 секунды со сверкой чисел. Поэтому несовместимость **закрыта**; её история полезна как пример того, почему mock-тест вызова нельзя считать доказательством совместимости внешнего API.

Для оценки «текст не хуже» нужна маленькая таблица из 3–5 характерных наборов: допустимый пример, набор с риском нового критического показателя, лучший набор, набор с лагом и набор у порога бюджета. Для каждого зафиксировать наличие сильных сторон, рисков, последствий, отсутствие внутренних имён полей, отсутствие выдуманных чисел и ручную оценку понятности. Сравнить медиану и максимум времени с прежними 16–18 секундами. Это сильнее, чем один удачный ответ.

### Цепочка доверия и границы вывода

[NIST о принципах объяснимого ИИ](https://www.nist.gov/publications/four-principles-explainable-artificial-intelligence) предлагает проверять, что объяснение действительно следует работе системы, понятно адресату и показывает границы применимости. Для нашего экрана это означает раскрываемую цепочку: исходный показатель → эффект меры с лагом → синергия → показатель района → взвешенная городская часть → слабейший район → штраф → итоговый Score. Все звенья должны извлекаться из расчёта, а не сочиняться моделью.

Не стоит выводить «уверенность 87%» или вероятностный интервал: для синтетических эффектов задания нет оценённой статистической ошибки. Следует разделять **точность вычисления по заданной формуле**, **чувствительность к изменению допущений** и **достоверность для реального города**, которая пока не установлена. [UK AQuA Book](https://www.gov.uk/guidance/the-aqua-book) отдельно рассматривает проверку реализации модели и пригодность модели для её назначения; [OECD](https://www.oecd.org/en/publications/foresight-toolkit-for-resilient-public-policy_bcdd9304-en.html) рекомендует исследовать несколько правдоподобных будущих и стресс-тестировать стратегии, а не выдавать один сценарий за предсказание.

Следующий компактный эксперимент: сравнить лучший по обычному Score набор с самым устойчивым на уже имеющихся условных событиях. Для каждого набора показать худший Score, максимальную потерю и число случаев с показателями ниже 40. Назвать это **стресс-тестом условных сценариев**, не вероятностным прогнозом. Добавление версии данных, хэша входных файлов, версии формулы и коммита в скачиваемый паспорт сделает конкретный результат воспроизводимым.

Записать измеренное время и версию проверенного коммита. В локальном прогоне сценарий занял 8,32 с, тогда как README обещает «примерно 2 секунды»; владельцу README стоит заменить обещание на проверенный диапазон или убрать оценку времени.
3. **P0 — пояснение границ модели.** В демо и документации говорить «условные данные и эффекты из ТЗ», не «прогноз бюджета/качества жизни реальной Астаны». Показать вклад мер и две причины компромисса.
4. **P1 — короткий сценарий жюри.** За 3 минуты пройти базу 52,56 → отказ сверх бюджета → пример 56,54 → улучшение 57,21 → условие про воздух 56,78 и цена 0,46 → утверждение человеком. Проверить, что экран и README называют те же числа.

По `AGENTS.md` и Положению нужны конкретные источники и лицензии сторонних библиотек, моделей, датасета и существенных заимствований. Владельцу README стоит добавить проверенную таблицу источников и отдельно обозначить OpenAI API как внешний сервис, а датасет — как предоставленный организаторами.

### После хакатона

1. **Источники и версия данных.** Для каждой меры хранить источник, дату, единицу, диапазон эффекта, владельца оценки и версию формулы. Показать эти поля в паспорте сценария.
2. **Неопределённость и устойчивость.** Давать диапазон Score при изменении эффектов, строить Pareto-наборы по Score, стоимости и слабейшему району; отмечать решения, которые устойчивы к изменению весов.
3. **Калибровка на факте.** Подключить 1–2 открытых городских набора данных, сравнивать прогноз с наблюдением и переоценивать коэффициенты. Географию и данные добавлять по одному проверенному направлению.
4. **Совместное обсуждение.** Карточка сценария, аргументы за/против, версии, статус рассмотрения и план/факт реализации по образцу платформ участия.
5. **Открытая архитектура моделей.** Версионированный контракт для альтернативных формул и датасетов, чтобы сравнивать не только решения, но и модельные допущения.

## Как оценивать следующую версию

Главный исследовательский вопрос: **помогает ли инструмент человеку находить более обоснованное решение, а не только больший Score?** Проверка: дать двум группам одинаковый кейс и время; одной — таблицу, другой — симулятор. Сравнить соблюдение бюджета, распознавание рисков, качество аргументации, время решения и способность объяснить последствия для слабейшего района. Score сам по себе не доказывает качество управленческого решения.

Для реального города обязателен другой уровень доказательств: происхождение данных, калибровка, неопределённость, независимая проверка и ответственность за утверждение. [NIST AI RMF](https://www.nist.gov/itl/ai-risk-management-framework) подчёркивает валидность, надёжность, прозрачность и объяснимость; [OECD](https://www.oecd.org/content/dam/oecd/en/publications/reports/2025/06/building-data-together_431b6387/725f7274-en.pdf/_jcr_content/renditions/original./725f7274-en.pdf) описывает пользу городских цифровых моделей для визуализации и участия вместе с ограничениями данных и приватности. Это ориентиры дальнейшей разработки, не утверждение о соответствии стандарту.
